## 1. Supabase access — ask this one first

Not a key. A permission. On August 16 2026 making a secret key on the
`xweueatikwvnahegeful` project failed with *"your account does not have the
necessary privileges to access this endpoint."*

Ask for it as a permission, not as a key, because the SAME permission is what
lets the console's SQL migrations run — and **a lot of them have never been
run.** Be careful how you say that number: there are 22 migration files in the
repo, the last recorded count was "eight of fourteen never run" (Aug 25), and
migrations 0018–0022 have no recorded state in `SETUP.md` or
`CONTEXT-FOR-AI.md` (0017 is recorded as unrun in a work-log file). The honest line is
"several are unrun and I can't tell you exactly how many until I can read the
database." One ask, two blockers gone.

**Say this:**

> My account can't create a secret key on `xweueatikwvnahegeful`, and the same
> permission is what the admin console's SQL migrations need. If that's a no,
> a service_role key named `admin_console` works instead — but the permission
> covers both.

If it is a no, the fallback key is:
**Supabase → Project Settings → API → `service_role` secret.**

**Also worth asking in the same breath:** the direct database connection string
(Supabase → Project Settings → Database → Connection string → URI). That is

## 3. Stripe — two keys, on purpose

Reading money and moving money are different risks. They should not share a key.

**Key A — read-only.** Powers monthly recurring revenue, active subscriptions,
the last 12 months of revenue, recent payments, and the paying half of the
Clients page.

> Stripe → Developers → API keys → **+ Create restricted key**, name it
> `admin-console-readonly`. Set **Read** on: Charges, Customers, Subscriptions,
> Prices, Invoices, Products, Balance. Everything else **None**.

**Key B — write, for invoices.** The read-only key can show an invoice; it
cannot create or send one. Managing invoices and orders from the console needs
a second key.

> Same screen, second key, name it `admin-console-invoices`. Set **Write** on:
> Invoices, Customers, Products, Prices, Subscriptions. Everything else **None**
> — no refunds, no payouts, no transfers, no key management.

**Say this out loud about Key B:** it turns on nothing today. Checked Aug 27
2026, the console never writes to Stripe — its invoices are rows in our own
database and Stripe's invoices are a read-only tab. Creating and sending an
invoice from the console is a feature we want, not one that exists.

**My pick: get both anyway.** Key B costs Andrew two minutes now and a whole
second conversation later. What I would not do is ask for one full-access key
instead — a leaked full key can move money, and this console will be open in a
browser tab all day on several machines.

**Do NOT set up the webhook today.** It is tempting — it is how the console
would learn a payment succeeded without asking. But there is no
`api/stripe-webhook.js` in the repo, so every delivery Stripe made would 404
and Stripe would start reporting our endpoint as failing. Ask for that secret
when the endpoint is built.

## What NOT to ask for

Asking for everything gets a "let me think about it". Leave these out:

- **Gmail.** No key from Andrew. It is one Google Cloud OAuth app created once
  by a Workspace admin. The growth@ password is not enough on its own — the app
  still has to exist. `SETUP.md` section 5 is click-by-click.
- **`VAULT_KEY` and `CRON_SECRET`.** Both are random strings generated locally.
  `openssl rand -base64 32` for the vault, Bitwarden's generator for the cron.
- **The plumbing keys** (`KV_*`, `REDIS_URL`, `FLAGS_SECRET`, `STATSIG_*`,
  `CMS_SECRET_KEY`, the `STRIPE_PRICE_*` list). Those belong to the platform's
  own deployment. The admin console is a separate Vercel project, so it does not
  inherit anything — it simply does not need them.

## After a key lands

1. Open `.env.local` in Cursor.
2. Paste the value after the `=`. No spaces, no quotes.
3. Terminal: **Ctrl+C**, then `npm run dev`.
4. **Do not use the Settings page as your proof.** It has six cards covering
   nine variable names, and while `VITE_NO_SIGNIN` is true it never asks the
   server at all — every row reads WAITING ON KEY however many keys you pasted.
   The widest report is `/api/health`, and it covers **13 flags, not 57 keys**
   — six of the live ones get no flag at all, and for those the proof is using
   the feature. Reading the 13 depends on where you are: **before** the Supabase
   service key is in, `/api/health` answers 200 with all 13 false and a note
   that the env vars are missing — that is not "every key is dead", ignore it.
   **After** it is in, the endpoint needs a signed-in member, so curl gets a
   401. Read it in the browser: set `VITE_NO_SIGNIN=false`, sign in for real,
   press **Cmd+Option+I** in Chrome, click **Network**, click **Settings** in
   the sidebar, click the row named **health**, then **Response**.
5. Same value into **Vercel → the admin project → Settings → Environment
   Variables**, ticking Production, Preview and Development. **Four exceptions
   — do not copy these to Vercel:** `GMAIL_REDIRECT_URI` and
   `CONNECT_REDIRECT_URI` (leave both blank there; the deployed site works its
   own address out), `ADMIN_BASE_URL` (localhost on the Mac,
   `https://admin.aisyndicate.com` in Vercel), and `VITE_NO_SIGNIN` (must be
   `false` in Vercel — `true` would deploy the console with the login screen
   switched off).
6. **Vercel → Deployments → newest → ⋯ → Redeploy.** Environment variables only
   take effect on a new deploy. Skipping this is why a key looks dead.
7. Bitwarden entry for it, the same minute.
